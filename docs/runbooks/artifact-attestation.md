# Runbook: Artifact Attestation and SBOM Failure

**Workflows:** `security-audit.yml` — Release SBOM / Verify Release Provenance; `frontend-build.yml` — Frontend Build Check (release path); `deploy-futurenet.yml` — SBOM and provenance upload
**Applies to:** `release-sbom`, `release-validation` jobs; SBOM generation steps in `deploy` job
**Owner:** @security-owner, @platform-owner
**Related:** [Runbook index](README.md) | [Frontend deploy runbook](frontend-deploy.md) | [Contract build runbook](contract-build.md)

---

## 1. Overview of the attestation pipeline

Each release produces three attestation artifacts that are attached to the GitHub release:

| Artifact | Generated by | Verifies |
|----------|-------------|---------|
| `sbom-rust.cdx.json` | `cargo cyclonedx` in `release-sbom` / `deploy` job | Rust dependency inventory in CycloneDX format |
| `sbom-node.cdx.json` | `@cyclonedx/cyclonedx-npm` in `release-sbom` / `frontend-build` | Node dependency inventory in CycloneDX format |
| `provenance.txt` / `provenance.json` | Collected from env in each workflow | Source revision, workflow identity, artifact digest |
| `sbom-digests.txt` | `sha256sum` of all CDX files | Digest manifest for independent re-verification |

The `release-validation` job re-downloads these from the release and independently verifies that:
- Both SBOM files are non-empty and have `bomFormat: CycloneDX` with at least one component.
- `provenance.txt` / `provenance.json` references the correct `source_revision` (the release commit SHA).
- The `workflow_identity` field matches the repository.
- The WASM digest in `provenance.json` is a valid 64-character hex string.
- `sha256sum -c sbom-digests.txt` passes (digest manifest matches actual files).

## 2. Diagnosis by failure type

### 2.1 SBOM generation failure — Rust

**Symptoms:** `cargo cyclonedx` exits non-zero; `sbom-rust.cdx.json` is absent or empty.

**Diagnosis:**
```bash
cd Dechat/stellar-contracts
cargo install cargo-cyclonedx --locked
cargo cyclonedx --format json --output-pattern package --output-cdx 2>&1
```

**Common causes and fixes:**

| Cause | Fix |
|-------|-----|
| `cargo-cyclonedx` not installed or wrong version | `cargo install --locked cargo-cyclonedx --version 0.5.5` |
| `Cargo.lock` absent | Run `cargo build` first to generate it |
| Workspace member resolution error | Ensure the manifest path argument points to the correct `Cargo.toml` |
| Output file path mismatch | Verify the `--override-filename` or `--output-cdx` flags match the expected filename |

**Verify the output:**
```bash
jq -e '.bomFormat == "CycloneDX" and (.components | length > 0)' sbom-rust.cdx.json
```

---

### 2.2 SBOM generation failure — Node

**Symptoms:** `@cyclonedx/cyclonedx-npm` exits non-zero or `sbom-node.cdx.json` is absent or empty.

**Diagnosis:**
```bash
cd Dechat/dex_with_fiat_frontend
pnpm dlx @cyclonedx/cyclonedx-npm --output-format json --output-file sbom-node.cdx.json 2>&1
```

**Common causes and fixes:**

| Cause | Fix |
|-------|-----|
| `node_modules` not installed | `pnpm install --frozen-lockfile` first |
| `pnpm-lock.yaml` out of sync | `pnpm install` to regenerate, commit the lockfile |
| Package resolution error during SBOM scan | Check for private registry access issues in CI environment |
| Output file permission error | Verify the working directory is writable |

**Verify the output:**
```bash
jq -e '.bomFormat == "CycloneDX" and (.components | length > 0)' sbom-node.cdx.json
```

---

### 2.3 Provenance file missing or malformed

**Symptoms:** `::error::Missing provenance file` or `jq` assertions fail on provenance fields.

**Diagnosis:**
Check which field failed in the validation step output. The validation checks:
1. `source_revision` equals the release commit SHA.
2. `workflow_ref` and `workflow_sha` are non-empty.
3. `wasm_sha256` matches `^[0-9a-f]{64}$`.

**Common causes and fixes:**

| Cause | Fix |
|-------|-----|
| `provenance.json` / `provenance.txt` not uploaded to the release | Re-run the `release-sbom` job (see §4) |
| `source_revision` in provenance does not match the release tag SHA | The release was published against the wrong commit; delete and re-create the release from the correct tag |
| `wasm_sha256` field is empty | The WASM artifact was not built before provenance collection; check the `build-wasm` job |
| `workflow_ref` is empty | The workflow env var `${{ github.workflow_ref }}` was not populated; re-run the job |

---

### 2.4 Digest manifest verification failure

**Symptoms:** `sha256sum -c sbom-digests.txt` fails with `FAILED` for one or more files.

**Cause:** An SBOM file was replaced or modified after the digest manifest was generated, or the upload was corrupted.

**Diagnosis:**
```bash
# Download all attestation assets from the release:
gh release download <tag> \
  --pattern 'sbom-*.cdx.json' \
  --pattern 'sbom-digests.txt' \
  --dir /tmp/verify-attestation

cd /tmp/verify-attestation
sha256sum -c sbom-digests.txt
```

If a file fails:
1. Compare the failing file size to what the generation step recorded in the step summary.
2. If the file is different: the release assets are corrupt or were tampered. Treat this as a security event and escalate to @security-owner.
3. If the file is simply missing: the upload step failed; re-upload (see §4).

---

### 2.5 Release validation job fails to download assets

**Symptoms:** `gh release download` exits non-zero; assets not found.

**Cause:** The SBOM upload step in the generation job failed before the validation job ran.

**Diagnosis:**
```bash
gh release view <tag> --json assets --jq '.assets[].name'
```

If the SBOM/provenance files are absent from the release, the generation step failed before uploading. Check the `release-sbom` job logs for the failed upload step.

**Fix:** Re-trigger the generation (see §4).

## 3. Safe retry procedure

**For transient failures** (network timeout during generation or upload):

Re-run only the `release-sbom` job from the Actions UI. The job is idempotent: it regenerates the same SBOMs from the same tag and re-uploads with `--clobber`, which replaces any partial uploads.

**For structural failures** (wrong SHA in provenance, wrong commit tagged):

1. Delete the GitHub release:
   ```bash
   gh release delete <tag> --yes
   ```
2. Delete the tag:
   ```bash
   git push origin --delete <tag>
   git tag -d <tag>
   ```
3. Create the correct tag from the right commit:
   ```bash
   git tag <tag> <correct-sha>
   git push origin <tag>
   ```
4. Re-create the GitHub release:
   ```bash
   gh release create <tag> --title "<title>" --notes "<notes>"
   ```
   The `release-sbom` and `release-validation` jobs will re-trigger automatically.

---

## 4. Re-triggering SBOM generation without deleting the release

If only the SBOM artifacts are missing (the release itself is correct):

```bash
# Re-publish the release to retrigger the workflow:
gh release edit <tag> --draft   # temporarily mark draft
gh release edit <tag> --draft=false  # re-publish
```

This fires a `release: published` event and re-runs both `security-audit.yml` (release-sbom job) and `frontend-build.yml` (release-validation job).

## 5. Verifying attestation independently

Any maintainer can re-verify the attestation chain without running CI:

```bash
TAG=<release-tag>
EXPECTED_SHA=$(git rev-list -n 1 "$TAG")

# Download release assets
gh release download "$TAG" \
  --pattern 'sbom-*.cdx.json' \
  --pattern 'provenance*' \
  --pattern 'sbom-digests.txt' \
  --dir /tmp/attest-verify

cd /tmp/attest-verify

# 1. Verify SBOM structure
for f in sbom-rust.cdx.json sbom-node.cdx.json; do
  jq -e '.bomFormat == "CycloneDX" and (.components | length > 0)' "$f" \
    && echo "✅ $f" || echo "❌ $f"
done

# 2. Verify provenance SHA
grep "$EXPECTED_SHA" provenance.txt || \
  jq -e --arg sha "$EXPECTED_SHA" '.source_revision == $sha' provenance.json
echo "✅ Provenance SHA matches tag $TAG"

# 3. Verify digest manifest
sha256sum -c sbom-digests.txt
echo "✅ Digest manifest verified"
```

## 6. Rollback procedure

SBOM and provenance artifacts are attached to a GitHub release and are read-only once published. There is no "rollback" of an attestation — if the attestation is wrong, the release must be re-created.

If a release with incorrect attestation has already been communicated externally:

1. Immediately notify @security-owner.
2. Do not delete the release until the incident is documented.
3. File a security advisory if the incorrect attestation could mislead downstream consumers about the contents of the release.
4. Create a corrected release with a patch version bump (e.g. `v1.2.1` to fix attestation errors in `v1.2.0`).

## 7. Escalation

| Condition | Escalate to |
|-----------|-------------|
| `sha256sum -c` fails (digest mismatch) | @security-owner immediately — potential release tampering |
| Provenance SHA does not match any known commit | @security-owner immediately — release may have been created from an unauthorized source |
| `sbom-node.cdx.json` has zero components | @platform-owner — SBOM generator may be scanning the wrong directory |
| `sbom-rust.cdx.json` has zero components | @contract-owner — `cargo-cyclonedx` may need a version update |
| Re-triggering attestation generation fails repeatedly | @platform-owner — may be a GitHub Actions permission or token scope issue |
